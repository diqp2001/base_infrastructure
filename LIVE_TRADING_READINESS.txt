ARCHITECTURE MAP (actual execution path, verified by reading the code on 2026-10-28)
--------------------------------------------------------------------------------
Data -> decision -> orders -> broker -> fills -> persistence:

 1. Engine clock  MisbuffetEngine._run_simulation / _execute_main_loop (engine/misbuffet_engine.py:422, 853) steps a
    configured interval (days / minutes, optional session window). Live mode reuses the same time-stepping loop: there
    is NO event-driven loop on streaming data. Each step: MarketDataService.create_data_slice (stored bars through
    the MarketDataHistoryService frontier) -> algorithm.on_data.
 2. Decision  project algorithm -> trading cycle (STM / CSM / SPX v2) -> target weights.
 3. Orders  UnifiedPortfolioManager.set_holdings (algorithm/unified_portfolio_manager.py:1103): gross cap, invalid
    targets, live-mode reconciliation gate (fail closed when live_mode and no reconciler, :1216), PositionReconciler
    pending tickers skipped, sells before buys -> TradeManager.execute_trade (algorithm/trade_manager.py:34).
 4. Submission  TradeManager: resolve holding/account -> submit_order_fn = algorithm.market_order -> engine transaction
    handler. Backtest: BacktestingTransactionHandler (simulated fill at the submission price). Live (_wire_live_trading,
    misbuffet_engine.py:932, fails hard without config.brokerage): BrokerageTransactionHandler ->
    BaseBroker.place_order (brokers/base_broker.py:153: connected check, _validate_order, optional PreTradeGate,
    in-memory self.orders) -> InteractiveBrokersBroker._place_order_impl (ibkr/interactive_brokers_broker.py:184:
    MARKET / LIMIT only, ib order id -> in-memory pending_orders) -> IBTWSClient.place_order.
 5. Broker events  IBTWSClient callbacks keep dicts in memory: orderStatus -> order_status (incl. permId), execDetails
    -> order_fills (execId, time, shares, price, side), openOrder, position / positionEnd, accountSummary, tickPrice /
    tickSize / tickGeneric / tickString -> market_data[reqId] (latest value + one receipt time), marketDataType (logged
    only), error (historical requests only routed to their request). _monitor_worker -> _process_order_updates turns
    orderStatus into OrderEvents, applying order_state.advances (forward-only; late / duplicate / out-of-order dropped).
 6. Persistence  TradeManager._book_atomically (unit_of_work.atomic, BI-006): Order (status FILLED) + Transaction
    (fill) + Position + cash, ONE transaction, written right after submission (trade_manager.py:77-111, 166).
 7. Valuation / monitoring  UnifiedPortfolioManager.get_portfolio_value (factor resolution), read-only /monitor
    dashboard (BI-023), project dashboards.

DEFECTS / GAPS FOUND IN P.01 (highest priority first)
---------------------------------------------------
 D1 CRITICAL  In live mode TradeManager books every order as FILLED, with a fill at the submission price, a position
              change and a cash movement, immediately after submission (trade_manager.py:77-111, status literal :166).
              The database would show fills that never happened. Must be split: live = record intent / SUBMITTED;
              fills, positions and cash only from broker executions. (P.03)
 D2 CRITICAL  No durable order intent before submission: TradeManager submits first, books after; the broker keeps
              ib order ids only in memory. A crash between submit and book loses the order. (P.03)
 D3 HIGH      Executions (execId), permId and commissions are memory-only; no commissionReport handler; no
              execId de-duplication across restarts. (P.03 / P.04)
 D4 HIGH      _cancel_order_impl forgets the order before IBKR confirms the cancel (interactive_brokers_broker.py:228).
 D5 HIGH      PreTradeGate and PositionReconciler exist and are tested but no live / paper broker attaches them. (P.05)
 D6 HIGH      Streaming market data: latest value only, receipt time only for the whole request, market-data type
              (live / frozen / delayed) not kept, entitlement errors (354, 10089, 10090, 10167, 10168, 10197) not
              routed to the subscription, no freshness / validity state, no reconnect / resubscribe. (P.02)
 D7 MEDIUM    No reconnect handling during a run; no recovery of open orders / executions into internal state. (P.04)
 D8 MEDIUM    Two OrderStatus enums with different stored spellings (BI-021 remaining). (P.03)
 D9 MEDIUM    Live enable is a single config flag; no separate "submission enabled" switch, no kill switch. (P.05/P.07)
 D10 MEDIUM   Live mode runs the backtest time-stepping loop on stored bars; there is no event-driven live loop. (P.06)
